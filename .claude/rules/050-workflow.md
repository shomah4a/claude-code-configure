# 作業プロセス

## 作業について

以下の手順で作業を進めること:
1. 作業計画を立案する
  - 作業計画のうち、調査の後の1つ目は開発ブランチの作成とすること
2. ユーザーに計画の承認を求める
3. 承認後に実装を開始する

- 計画策定時は防衛的計画評価評価エージェントも利用して計画を評価すること
  - エージェントへの入力にはユーザーが実装依頼した内容もそのまま含めること
- 設計をレイヤリングし、動作確認できる最小単位で一個一個組み立てていくこと
- コミットはビルドが通る単位とし、細かくコミットを重ねていくこと
  - すべての修正が終わったあとに変更単位でコミットするのではなく、意味のある修正が終わり次第コミットしていくこと
  - あとから内容を分割してコミットすると分割単位がおかしくなったりしてしまう
- 実装が終わったら実装内容を実装安全性評価エージェントに評価してもらうこと
  - エージェントへの入力にはユーザーが実装依頼した内容もそのまま含めること
  - 優先度HIGH,CRITICALの指摘があった場合は修正対応を行い、再度評価してもらうこと
  - HIGH, CRITICAL の指摘がない場合は残りの指摘をリストしてユーザーの指示を仰ぐこと
- 計画文書は `.claude/tmp/YYYY-MM-DD_<タスク概要>.md` として保存すること
  - plan mode のときはplan承認要求前に書き出すこと


### 評価エージェントの出力の結果の取り扱い

1. エージェントの評価結果をそのまま `.claude/tmp` に書き出す
  - サマライズはしない
2. コンソールにサマライズを出力する

## バグフィックスなどをするとき

原因となる箇所が判明するまでは修正をしてはいけない。

以下のようなフローで修正していけるとよい
- 原因となる箇所の探索
- テストコードによる再現
  - 想定通り再現しない場合は原因探索に戻る
- 修正
- テストコードが想定通りに動作するかチェック
