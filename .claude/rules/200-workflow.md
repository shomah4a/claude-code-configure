# 作業プロセス

このプロセスはタスク全体のオーケストレーション規約であり、メインエージェントに適用する。委譲された個別タスクの実行には適用しない。

## 作業について

以下の手順で作業を進めること:
1. 作業計画を立案する
  - 作業計画のうち、調査の後の1つ目はworktreeの作成とすること
2. ユーザーに計画の承認を求める
3. 承認後に実装を開始する

- 計画策定時は防衛的計画評価評価エージェントも利用して計画を評価すること
  - エージェントへの入力にはユーザーが実装依頼した内容もそのまま含めること
- 設計をレイヤリングし、動作確認できる最小単位で一個一個組み立てていくこと
- コミットはビルドが通る単位とし、細かくコミットを重ねていくこと
  - すべての修正が終わったあとに変更単位でコミットするのではなく、意味のある修正が終わり次第コミットしていくこと
  - あとから内容を分割してコミットすると分割単位がおかしくなったりしてしまう
- 実装が終わったら実装内容を実装安全性評価エージェントに評価してもらうこと
  - エージェントへの入力にはユーザーが実装依頼した内容もそのまま含めること
  - 優先度HIGH,CRITICALの指摘があった場合は修正対応を行い、再度評価してもらうこと
  - HIGH, CRITICAL の指摘がない場合は残りの指摘をリストしてユーザーの指示を仰ぐこと
- 計画文書は `.claude/tmp/YYYY-MM-DD_<タスク概要>.md` として保存すること
  - plan mode のときはplan承認要求前に書き出すこと
- 作業経過は計画文書とは別に `.claude/tmp/YYYY-MM-DD_<タスク概要>_progress.md` に記録すること
  - 記録するタイミング: コミット時、PR 単位の作業完了時、計画からの逸脱が発生した時、作業を中断してユーザーの確認を待つ時
  - 記録する内容: 完了した作業項目、着手中の項目、作成したコミットと PR、計画からの逸脱とその理由、未解決の課題
- 実装を開始した後は計画文書を編集しないこと
  - 計画の変更が必要になった場合は作業を中断してユーザーに報告し、指示に従って新しい計画文書を作成する。元の計画文書は残す
  - 実装を破棄して計画の修正から再実装する際に、元の計画と経過を対比できるようにするための規則である


### 計画文書・経過文書の履歴管理

`.claude/tmp` 配下の計画文書、経過文書、評価エージェントの出力は RCS で履歴を残すこと。
履歴の実体は `.claude/tmp/RCS/` に置く (存在しなければ `mkdir -p .claude/tmp/RCS` で作る)。
worktree で作業しているときも main 側の `.claude/tmp` を対象とする。

- 登録のタイミングは「ひとまとまりの編集が済んだ時点」とする
  - 1 回の意図した変更のために複数箇所を編集した場合、その一連の編集が終わってから 1 回登録する。編集操作のたびに登録しない
  - 目安: 計画文書なら節の追加や修正が一通り終わった時、経過文書なら 1 回の記録が終わった時、評価出力なら書き出した直後
- 操作は `ci -l` に統一する
  - 初回: `ci -l -m"<変更内容>" -t-"<タスク概要> <文書種別>" <file>`
  - 2 回目以降: `ci -l -m"<変更内容>" <file>`
  - `-l` によりロック付きで作業ファイルが書込可のまま残る。`-l` を付けずに実行すると作業ファイルが削除されるため必ず付ける
- ログメッセージ (`-m`) は日本語で、何を変更したかを書くこと (例: `コミット 0ecb3b5 を記録`, `防衛的計画評価の指摘を反映`)
- 履歴の参照
  - 一覧: `rlog <file>`
  - 版間の差分: `rcsdiff -r1.1 -r1.3 <file>`
  - 過去の版の内容: `co -p -r1.2 <file>`
- 本規則の適用前から存在するファイルは、次に編集した時点で初回登録する


### 作業の分割

- 変更が複数のリポジトリまたは複数の関心事 (インフラ、CI、バッチ、アプリケーションなど) に及ぶ場合、リリース可能な単位ごとに PR を分割すること
  - 分割単位は「1 PR につき 1 関心事」とする。同一リポジトリ内でも関心事が異なれば PR を分ける
  - 各 PR は、他の PR が未リリースの状態でも単独でリリースして支障が出ない内容にすること。相互に依存する PR を作ってはならない
- PR の順序は被依存側 (他から利用される側) を先にすること
  - 例: ECS バッチの結果を S3 経由でアプリケーションが読み込む場合
    1. IaC リポジトリで ECR リポジトリ作成
    2. IaC リポジトリで S3 バケット作成 (1 とは順不同)
    3. バッチリポジトリで ECS バッチ実装
    4. バッチリポジトリでマージ時に ECR push する GitHub Actions 実装
    5. バッチリポジトリで CDK による起動設定 (EventBridge rule によるスケジュール)
    6. アプリケーションロールへの S3 権限付与
    7. アプリケーション実装
  - 相互に依存しない PR 同士の順序は問わない
- 作業計画には PR の分割単位と順序を列挙し、計画承認の対象に含めること
- 1 つの PR の作業が完了したら作業を中断し、ユーザーによる確認とリリースを待つこと。ユーザーからリリース完了の連絡を受けてから次の PR に着手する
  - 複数の PR を並行して作業しないこと
  - 一気に進めてしまうと確認の内容によっては手戻りが大きくなってしまう。これを避けるために確認ステップを小さく保つ


### 改修とリファクタリングの分割

改修作業の前にリファクタリングを行ったほうがいよいケースは、リファクタリングを別タスクとして切り出し、リファクタとそのリリース後に改修を行うこと


### 評価エージェントの出力の結果の取り扱い

以下の2つを両方実行すること:

1. エージェントの評価結果を `.claude/tmp` にファイルとして書き出す
   - エージェントが返却したテキストを加工・要約せず、そのまま全文を書き出すこと
   - 自分の言葉で書き直したり、項目を省略したりしてはならない
2. コンソールにはサマリーを出力する
   - ファイルに書き出した内容の要約をユーザー向けに表示する


## バグフィックスなどをするとき

原因となる箇所が判明するまでは修正をしてはいけない。

以下のようなフローで修正していけるとよい
- 原因となる箇所の探索
- テストコードによる再現
  - 想定通り再現しない場合は原因探索に戻る
- 修正
- テストコードが想定通りに動作するかチェック
